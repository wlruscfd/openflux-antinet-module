# Бамп апстрима модуля: процедура

Как поднять вендоренный апстрим модуля на новую версию, не потеряв интеграционный слой AntiNet.
Контракт модуля — `MODULE_API.md`, сборка из готового состояния — `README.md`.

```bash
python build.py --module <модуль> --bump <тег|ветка|коммит>
```

Эта команда делает шаг 2 из семи. Остальные шесть — ваши, и пропуск любого из них теряет работу:
шаг 1 (патч-слой коммитом) — молча, шаг 4 (фиксация разрешения) — на следующем бампе.

---

## ⛔ Метод ровно один: слияние

У модуля два слоя: **апстрим автора** и **интеграционный слой AntiNet** (точки входа, protect-хук,
разговор с хостом). Бамп обязан обновить первый, не тронув второй.

**Инвариант метода: ваш слой обязан быть одной из сторон слияния.** Тогда git физически не может
выбрать апстрим молча — любая коллизия становится маркером `<<<<<<<` в файле. Ни один другой
способ этим свойством не обладает:

| способ | что делает на самом деле |
|---|---|
| `cp -r` нового апстрима поверх дерева | у копирования нет стороны слияния: конфликта не существует, показывать нечего |
| `git apply --3way` | базой берёт апстримный блоб. Ваш патч в слиянии не участвует вовсе, апстримная сторона выбирается без единого маркера |
| перенос правок руками | работа, которой не должно быть; проверяется только глазами, а глаз пропускает |
| `git stash` на время бампа | уносит патч-слой целиком, `stash drop` необратим |

Ни один из них не «быстрее в простом случае»: простой случай — это слияние без конфликтов, оно
занимает секунды. Тянет сделать руками — значит не хватает стороны слияния, и чинить надо
это (материализовать коммит), а не обходить метод.

⚠ **Каждая git-команда пишется с явным `--git-dir=`.** Голый `git` внутри дерева адресует тот
репозиторий, в чьей рабочей копии вы стоите, и это почти никогда не тот, который имелся в виду:
над деревом модуля стоят два разных гита — ваш репозиторий и бамп-гит.

## 1. Координаты апстрима в `module.json`

Объявляются один раз, в секции `build` — она нужна только при сборке и хосту не отдаётся:

```json
"build": {
  "goDir": "native/<ваше дерево>",
  "goPkg": "./cmd/helper",
  "upstream": {
    "url":    "https://github.com/<вы>/<репозиторий>",
    "base":   "v1.4.3",
    "prefix": "go_client"
  }
}
```

| поле | смысл |
|---|---|
| `url` | откуда тянуть. Нужна именно история, а не снимок: без неё не найдётся общий предок и слияние выродится в перезапись |
| `base` | ревизия апстрима, на которой ваше дерево стоит сейчас. Обновляется после каждого успешного бампа — это и есть реестр баз |
| `prefix` | только если апстрим держит код в подкаталоге (раскладка Б) |
| `take` | только если модуль берёт из апстрима выборку (раскладка В) |
| `dir` | только если вендоренный апстрим лежит **не** в `goDir` — путь от каталога модуля |

⚠ **`dir` нужен модулю, у которого апстрим вообще не Go.** У csqtt вендорен rust-движок
(`native/csqtt-engine` ← апстримный `rust-client/`), а `goDir` — целиком своя обвязка, которой в
апстриме нет: бамп по `goDir` синтезировал бы сторону слияния из каталога, не имеющего к апстриму
отношения. Без `dir` бампается `goDir` — это и есть обычный случай.

### 1.1 Три раскладки — ровно одна ваша

| раскладка | когда | что становится стороной слияния |
|---|---|---|
| **А. Совпадает** | дерево модуля = дерево апстрима | апстримный коммит как есть |
| **Б. `prefix: "<подкаталог>"`** | апстрим держит код в подкаталоге, у вас он распластан в корне модуля | синтетический коммит, чьё дерево — этот подкаталог |
| **В. `take: "ours"`** | модуль берёт из апстрима выборку (апстрим — большой репозиторий, вам нужна его часть) | апстрим, ограниченный путями, которые в вашем дереве уже есть |

Как это выглядит на живых модулях:

| модуль | апстрим | раскладка |
|---|---|---|
| `masterdns` | `masterking32/MasterDnsVPN` | **А** — дерево совпадает с апстримом |
| `qwdtt` | `SpaceNeuroX/proxy-turn-vk-android` | **Б** — `prefix: "go_client"` |
| `openflux` | `wlruscfd/openflux-server` | **В** — `take: "ours"`: из большого репозитория берутся `transport/`, `network/`, `utils/` и часть `tunnel/` |
| `echo` | своего апстрима нет — это образец | — |

Выборка в раскладке В не пишется списком путей — она выводится из факта, то есть из того, какие
файлы у вас лежат. Список руками устарел бы первым же апстримным переименованием, и разошёлся бы
молча.

⚠ **Следствие раскладки В: новый файл апстрима бамп не принесёт** — его у вас нет, значит в сторону
слияния он не попадает. Это свойство модели, а не потеря; что с этим делать — § 6.

В раскладках Б и В синтетические `upstream`-коммиты связываются в цепочку (каждый следующий —
потомок предыдущего). Без цепочки у следующего бампа не найдётся общего предка.

### 1.2 Что бамп не меняет

⛔ **`version` модуля — ваша нумерация обёртки, и бамп апстрима её не двигает.** Версия отвечает на
вопрос «что изменилось в модуле для пользователя», а не «какой апстрим внутри». Апстрим может уйти
на три релиза вперёд, не поменяв в модуле ни строки поведения — версия при этом остаётся прежней.
Поднимать её надо тогда, когда меняется сам модуль.

## 2. Как устроен бамп-гит

Дереву модуля не нужен свой `.git` — и заводить его нельзя: ваш репозиторий немедленно увидит
вложенный репозиторий и заменит сотни отслеживаемых файлов на gitlink.

Поэтому каталог гита лежит вне дерева — `.bumpgits/<модуль>.git` рядом с `build.py`, а рабочим
деревом ему указана папка модуля (`core.worktree`). Внутри дерева не появляется ничего.

| ветка | что это |
|---|---|
| `upstream` | чистый апстрим на базовой ревизии; при бампе на неё встаёт новая версия |
| `<модуль>` | апстрим-база + **ваш интеграционный слой** коммитами поверх неё |

Бамп = `git merge upstream` в ветку модуля. Бамп-гиты под контроль версий не берутся намеренно:
они восстанавливаются этой же командой из `build.upstream.base` — поэтому поле `base` обязано быть
актуальным.

⚠ **Бамп-гит настроен на `core.autocrlf=true`.** Вендоренные деревья часто лежат на диске в CRLF,
апстрим хранит LF. Без нормализации бамп-гит объявил бы изменёнными все файлы — патч-слоем стало бы
всё дерево, и слияние потеряло бы смысл. Из этого же следует, что любой ручной `diff` по этим
файлам делается с `--strip-trailing-cr`.

## 3. Процедура: семь шагов

### Шаг 1. Патч-слой обязан быть коммитом

Первый бамп заводит бамп-гит сам и коммитит текущее состояние дерева как ваш слой. Дальше это ваша
обязанность: **правите вендоренный файл — коммитите в оба гита** (свой репозиторий — истина,
бамп-гит — сторона будущего слияния).

```bash
git --git-dir=.bumpgits/<модуль>.git status --short     # должно быть пусто
```

Пока правка лежит рабочим слоем, а не коммитом, она не является стороной слияния: git возьмёт
апстрим и не покажет ничего. Команда бампа это проверяет и отказывается работать (§ 8), но проверка
спасает только от потери в этом бампе — она не заменяет привычку.

### Шаг 2. Слияние

```bash
python build.py --module <модуль> --bump <ref>
```

Что команда делает по порядку: заводит или доводит бамп-гит → проверяет, что в дереве нет
незакоммиченного → `fetch` апстрима → строит сторону слияния по вашей раскладке → сравнивает её
дерево с текущим `upstream` → сливает в ветку модуля → печатает список конфликтов.

Чего команда не делает: не коммитит разрешение конфликтов, не трогает `module.json`, не собирает,
не запускает тесты, не коммитит в ваш репозиторий. Это шаги 4–7.

Слияние без конфликтов — нормальный исход, а не повод для подозрений; проверка того, что при этом
ничего не потеряно, — § 5.

### Шаг 3. Разрешение конфликтов

Конфликты приходят обычными маркерами в реальные файлы дерева модуля. Разрешаются они там же, по
правилам § 4. После правки файл должен собираться: `go build ./...` в каталоге модуля.

### Шаг 4. Зафиксировать разрешение в бамп-гите

```bash
git --git-dir=.bumpgits/<модуль>.git add -- <файлы>
git --git-dir=.bumpgits/<модуль>.git commit -m "resolve merge with <ref>"
```

⛔ **Пропуск этого шага теряет работу на следующем бампе, а не на этом.** Незафиксированное
разрешение остаётся рабочим слоем — то есть перестаёт быть стороной слияния ровно в том же смысле,
что и на шаге 1. Проверка та же: `git --git-dir=.bumpgits/<модуль>.git status --short` пуст.

То же касается правок, сделанных после коммита слияния (дочистили комментарий, переименовали) —
они тоже идут в бамп-гит, иначе следующий бамп их не увидит.

### Шаг 5. Обновить `base`

В `module.json` → `build.upstream.base` ставится ревизия, на которую только что влили. Это
единственный реестр баз: он живёт в дескрипторе, а не отдельным файлом, потому что отдельный файл
неизбежно разошёлся бы с тем, что реально читает команда.

`version` при этом не трогается (§ 1.2).

### Шаг 6. Сборка под все цели и тесты

```bash
python build.py --module <модуль> --os all
python build.py --module <модуль> --test
```

Обе команды обязательны и не заменяют друг друга: сборка проверяет кросс-компиляцию под каждую
цель, `--test` гоняет тесты main-пакета с инжектированными канонами под хост-ОС.

⚠ Платформенная половина канона проверяется тестом только на своей ОС — если правили что-то
платформенное, `--test` стоит прогнать и на второй.

Есть тесты с `-race` (например, вокруг разделяемого состояния) — прогнать и их: гонку не видит ни
сборка, ни обычный тест.

### Шаг 7. Коммит в свой репозиторий

Дерево модуля коммитится как обычно, поимённо. В том же коммите: обновлённый `module.json` и доки
модуля, если бамп изменил список расхождений с апстримом.

## 4. Разрешение конфликтов

### 4.1 В маркерах, а не заменой стороны

`git checkout --ours <файл>` / `--theirs <файл>` выглядят как разрешение конфликта, но они
выбрасывают вторую сторону целиком — включая то, что в ней не конфликтовало. Дальше остаётся
дописать потерянное руками, то есть ровно тот перенос правок руками, от которого и защищает
слияние: git больше не сторож, сторожем становится ваша память.

Правильный ход — редактировать участок между `<<<<<<<` и `>>>>>>>`: всё, что слияние развело без
конфликта, при этом остаётся нетронутым.

Замена стороны законна ровно в одном случае — когда конфликт целиком сводится к одной стороне
(апстрим переписал только комментарии в файле, который вы переписали целиком). Это надо не
предположить, а посмотреть: `git diff <база>..<новый ref> -- <файл>`.

### 4.2 Маркер — не смысловая единица

Маркер охватывает строки, которые разошлись, а не функцию целиком: **хвост той же функции может
лежать за `>>>>>>>`** и быть взят вашей стороной автоматически. Выбрать в маркере апстримную
сторону и не посмотреть дальше — значит склеить апстримное начало со своим хвостом.

Живой случай: в маркере разошлось только условие `if` в функции переподключения, а `return` и весь
блок пробуждения ожидания остались ниже. Механический выбор апстримной стороны дал бы функцию,
которая больше не будит ожидание backoff — и собралась бы она без единого замечания.

**Поэтому после разрешения читается функция целиком, а не diff.**

### 4.3 Категории конфликтов

| что конфликтует | как решать |
|---|---|
| доки, `.github/`, сгенерированное | взять апстримную сторону |
| ваша правка против апстримной правки в одном месте | слить построчно, сохранив **обе** |
| апстрим переписал функцию, которую вы патчили | перенести замысел правки в новый код, а не её строки |
| апстрим удалил файл, который вы слегка меняли | принять удаление, проверив, куда переехала функциональность |
| апстрим сам решил ту же задачу, что и ваша правка | взять апстримную сторону и снять расхождение из доков модуля |

⚠ «Взять апстрим» законно только там, где ваша правка объективно исчезла как задача. Если правка
всё ещё нужна, а слить трудно — трудность не аргумент: ваш слой существует, потому что без него
что-то ломается.

Последняя строка таблицы — лучший исход бампа: расхождений стало меньше. Но она требует доказать,
что апстримное решение закрывает ту же задачу, а не похоже на неё внешне. Доказательство — разбор
апстримного кода на том сценарии, ради которого делалась ваша правка.

### 4.4 Если сторона всё же была заменена

Результат проверяется двумя сверками, а не глазами:

```bash
# 1. апстримного кода не потеряно: удалений против нового апстрима быть не должно
git --git-dir=.bumpgits/<модуль>.git diff --numstat upstream..<модуль> -- <файл>

# 2. своего кода не потеряно: каждая ваша строка присутствует в результате
git --git-dir=.bumpgits/<модуль>.git diff <старый upstream-коммит>:<файл> <ваш коммит>:<файл>
```

Сверка сильнее: воспроизвести то же слияние пофайлово и сравнить с тем, что получилось.

```bash
D=.bumpgits/<модуль>.git
git --git-dir=$D show <ваш коммит до слияния>:<файл>  > /tmp/ours
git --git-dir=$D show <старый upstream-коммит>:<файл> > /tmp/base
git --git-dir=$D show <новый upstream-коммит>:<файл>  > /tmp/theirs
git merge-file -p --diff3 /tmp/ours /tmp/base /tmp/theirs > /tmp/merged
```

`/tmp/merged` показывает, что git слил бы сам и где именно требуется человек. Расхождение вашего
результата с этим файлом вне маркеров — потеря.

## 5. Пост-верификация: четыре среза

Ни один не заменяет другой.

**1. Интеграционный слой против нового апстрима.**

```bash
git --git-dir=.bumpgits/<модуль>.git diff --stat upstream..<модуль>
```

Список должен состоять из ваших файлов и ваших правок — ничего апстримного там быть не должно.
Знакомого файла в списке нет → слияние взяло апстримную сторону, смотрите его в дереве.

**2. Тот же список в `--numstat`.** Файл с нулём удалений — это апстримный файл плюс ваши строки,
то есть апстримная сторона цела по построению. Файл с удалениями требует объяснения каждому: это
ваш осознанный вырез (клиент-only вместо клиент+сервер) или потеря?

**3. Сверка с документированным списком расхождений.** Перечень из § 4.3 в доках модуля сверяется
с фактическим списком из среза 1. ⚠ **Потерянная правка невидима для любого диффа с апстримом** —
после потери файл апстриму равен, и дифф о ней молчит. Ловит её только этот срез.

**4. Сборка под все цели и тесты** — шаг 6.

## 6. Две вещи, которых слияние не видит

**Ваш файл с кодом апстрима внутри.** Скопировали пару функций из апстримного файла, который
целиком не берёте, в свой файл рядом — апстрим о таком файле не знает, и бамп его не обновит
никогда. Расхождение накапливается молча. Такие выноски перечисляются в доках модуля и сверяются
при каждом бампе:

```bash
git --git-dir=.bumpgits/<модуль>.git show <новый ref>:<апстримный файл-источник>
```

**Новый файл апстрима (раскладка В).** Апстрим вынес код в новый файл — у вас его нет, значит в
сторону слияния он не попал, а обновлённый файл, который на него ссылается, перестанет собираться.
Ошибка `undefined: <пакет>.<Символ>` сразу после бампа читается именно так.

Лечится подключением недостающего файла, а не откатом бампа:

```bash
git --git-dir=.bumpgits/<модуль>.git show <новый ref>:<путь> > <путь>
git --git-dir=.bumpgits/<модуль>.git add -- <путь>
```

После этого файл становится частью выборки и дальше бампается сам.

## 7. Запрещено

| действие | почему |
|---|---|
| `cp -r` апстрима поверх дерева | нет стороны слияния, коллизия разрешается молча |
| `git apply --3way` для апстрим-дельты | базой берёт апстримный блоб, ваш патч в слиянии не участвует |
| `git checkout --ours/--theirs` как способ разрешения | выбрасывает и то, что не конфликтовало (§ 4.1) |
| `git stash` на время бампа | уносит патч-слой целиком, `drop` необратим |
| `.git` внутри дерева модуля | ваш репозиторий заменит сотни файлов на gitlink |
| правка вендоренного файла без коммита в бамп-гит | правка перестаёт быть стороной слияния — потеря на следующем бампе |
| `git clean -fd` в дереве модуля | убивает файлы, которых бамп-гит не отслеживает |
| поднять `version` из-за бампа апстрима | версия — про модуль, не про апстрим (§ 1.2) |

## 8. Troubleshooting

Сообщения — те, что печатает сама команда.

**`в module.json нет build.upstream.{url,base} — бампать нечем`.** Координаты не объявлены — § 1.

**`в дереве есть незакоммиченное — слияние взяло бы апстрим молча`.** Шаг 1: закоммитьте правки в
бамп-гит, они и есть ваша сторона. Команда печатает первые десять файлов.

**`ревизии '<ref>' нет в апстриме — сверь build.upstream.base`.** Обычно апстрим переписал историю
(force-push) и записанная база стала недостижимой. Базой берётся ближайший достижимый коммит,
расхождение разбирается слиянием как обычно.

**`в <ref> нет подкаталога '<prefix>'`.** Апстрим переехал: подкаталог переименован или код поднят
в корень. Раскладка в `module.json` (§ 1.1) больше не описывает апстрим — поправьте её.

**`апстрим не изменился — бампать нечего`.** Сторона слияния совпала с текущей по дереву. Значит в
апстриме изменилось то, чего у вас нет: релиз тронул только те каталоги, которые модуль не берёт.

**Слияние прошло, но в дереве ничего не изменилось.** То же самое, увиденное с другой стороны: база
переставлена, следующий бамп пойдёт от неё. Бамп осмыслен и в этом случае.

**Последний тег апстрима старше вашей базы.** Бывает, если автор тегает редко. Бампайте на
конкретный коммит ветки — команда принимает любой ref.

**После бампа `undefined: <пакет>.<Символ>`.** Апстрим вынес код в новый файл — § 6.
